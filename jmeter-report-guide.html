JMeter HTML 리포트 분석 가이드 load-tester 프로젝트 · 결과서(REPORT-GUIDE.md) 작성을 위한 대시보드 판독법

0. 리포트 생성과 열기

REPORT=1 ./scripts/run-target-tps.sh 10000 <서버IP> 18080 300     # 실행과 동시에 생성
JVM_ARGS=-Xmx6g jmeter -g results/result_xxx.jtl -o results/report_xxx/   # 기존 jtl에서 생성

results/report_xxx/index.html을 브라우저로 연다. 좌측 메뉴가 Dashboard(요약) / Charts(그래프 3분류)로 나뉜다.

1. 5분 분석 루틴 — 이 순서로만 보면 된다

합격/불합격 즉답 — Dashboard의 Statistics 표
Dashboard → Statistics
Error % 와 99th pct 두 열만 먼저 본다. 에러율 기준 초과 또는 p99가 SLA 초과면 이후 분석은 "왜 실패했나" 모드로 전환.
부하가 계획대로 걸렸나 — TPS 그래프
Charts → Throughput → Transactions Per Second
고정 TPS 테스트면 목표값에서 평평해야 한다. 출렁이면 발생기·서버 어느 쪽이든 조절 실패 → 측정 신뢰도부터 의심.
버텼나, 버티는 척했나 — 응답시간 추이
Charts → Over Time → Response Times Over Time
이 가이드의 핵심 그래프. 아래 패턴 판독표로 모양을 해석한다. TPS가 평평해도 응답시간이 우상향이면 불합격 예비군.
에러의 정체 — Errors 표
Dashboard → Errors
같은 1%라도 500(서버 로직)과 Connection refused(수용 한계)와 timeout(대기열)은 원인·조치가 전혀 다르다. 아래 3-3 참고.
꼬리 확인 — Percentiles
Charts → Response Times → Response Time Percentiles
곡선이 90% 이후 급격히 꺾여 오르면 "대부분 빠른데 일부가 심하게 느림" = 간헐 이벤트(GC·커넥션 재수립·락). 완만하면 전반적 부하 반응.

2. 화면별 해설

2-1. APDEX (Dashboard 최상단)

만족도 지수: (만족 표본 + 허용 표본/2) ÷ 전체. 기본 임계값은 만족 ≤ 500ms, 허용 ≤ 1.5s. 1.000이면 전 표본이 500ms 이내라는 뜻.

APDEX해석
0.94 ~ 1.00우수
0.85 ~ 0.94양호 — p99 확인 필요
< 0.85문제 — 응답시간 분석 필수

SLA가 100ms처럼 엄격하면 기본 임계값 500ms는 너무 관대하다. 생성 시 -Jjmeter.reportgenerator.apdex_satisfied_threshold=100 으로 조정 가능.

2-2. Statistics 표 — 열 읽는 법

열의미결과서 사용
#Samples / KO총 요청 수 / 실패 수표본 규모 명기
Error %실패 비율합격 기준 1순위 (기준 예: ≤ 0.1%)
Average평균 응답 (ms)참고용 — 평균 단독 인용 금지
90th / 95th / 99th pct상위 백분위 응답p99가 실질 품질 지표
Min / Max최소/최대Max 스파이크 시 Over Time에서 시점 추적
Throughput초당 처리 (≈TPS)목표 대비 달성률
KB/sec (recv/sent)대역폭 사용NIC 한도 대비 (FORMULAS ④)
함정: 이 표는 램프업 구간을 포함한 전체 평균이다. 정상상태 수치가 필요하면 ./scripts/summarize-jtl.sh <jtl> <램프업초> 로 재계산해서 결과서에 쓴다. 리포트 표와 요약 스크립트 수치가 다른 이유가 이것.

2-3. Errors 표 — 에러 유형별 의미

에러 텍스트뜻의심 지점
500 / 502 / 503서버가 받긴 했으나 실패 응답앱 로직, 다운스트림(DB), 워커 고갈(503)
Connection refused연결 자체를 거부서버 다운, accept 큐(somaxconn), 방화벽
Connection timed out연결 시도 응답 없음SYN 큐 포화, conntrack, 네트워크
Read timed out / failed to respond연결 후 응답 안 옴서버 처리 지연, keep-alive 강제 종료
Can't assign requested address발생기 포트 고갈서버 문제 아님! TUNING.md 1장
Assertion failed응답은 왔으나 내용 불일치앱 응답 규격, 부분 실패

2-4. Response Times Over Time — 패턴 판독표

평평 (수평 유지)
정상. 부하 전 구간에서 안정적으로 소화 중. 결과서에 "유지 확인"으로 기록.
우상향 (지속 상승)
무언가 누적되고 있다 — 커넥션 누수, 큐 적체, 메모리 증가, DB 풀 고갈. soak 테스트에서 이 패턴이면 불합격. 서버 메모리 추이와 대조할 것.
주기적 톱니 (규칙적 스파이크)
주기성 = GC(서버 또는 발생기 JVM), 스케줄 작업, 캐시 만료. 간격이 일정하면 GC 가능성 높음 — 서버가 Java면 GC 로그, 발생기면 힙 증설/인스턴스 분할(run-multi) 검토.
단발 스파이크
일시 이벤트 — 재시도 폭주, 네트워크 순단, 이웃 VM 간섭(%st). 발생 시각을 서버 access 로그(proc_us)와 대조: proc_us도 튀었으면 서버 내부, 아니면 경로 문제.
계단형 (단계별 상승)
임계 통과의 신호 — 워커 풀 소진 → 큐잉 시작, 커넥션 한도 도달 등. 계단 시작 시점의 TPS/스레드 수가 곧 그 자원의 한계 용량이다. max-tps 분석에서 중요.

2-5. 나머지 그래프 활용

그래프위치보는 이유
Active Threads Over TimeOver Time램프업이 계획대로 됐는지. run-multi 병합 리포트에선 인스턴스당 수치로 표시됨(실제는 ×N)
Latencies Over TimeOver TimeLatency(첫 바이트)와 응답시간 차이 크면 = 본문 전송이 느림(대역폭)
Time Vs ThreadsResponse Times스레드 수 증가에 따른 응답 변화 — 선형 상승 시작점이 포화점
Response Time DistributionResponse Times봉우리가 2개면 두 종류 경로 존재(캐시 히트/미스, GC 걸린 요청)
Codes Per SecondThroughput에러가 특정 시간대에 몰렸는지 분산됐는지

3. 시나리오별 체크포인트

시나리오반드시 볼 것합격 판정
목표 TPS 유지
(run-target-tps)		 TPS 그래프 평탄성, Error %, p99, 응답 추이 TPS 목표±2% 평탄 + 에러≤0.1% + p99≤SLA + 응답 그래프 평평
최대 TPS
(run-max-tps)		 단계별 Throughput, Time Vs Threads, 한계 도달 시 에러 유형 정체점 = 용량. 한계에서 "에러 폭발"이 아닌 "지연 상승"이면 graceful → 견고성 가점
vUser
(run-vusers / run-multi)		 TPS ≈ 예상치(vUser÷think), Error %, p99 예상 TPS 도달 + 에러 0% + p99 안정
Soak (1시간) Over Time 그래프 전부 — 추이가 전부다 TPS·p99 그래프가 끝까지 수평 + 서버 메모리 무증가

4. 자주 하는 실수

① 평균만 인용 — 평균 5ms + p99 2초 = 100명 중 1명은 2초 대기. 결과서엔 항상 avg/p95/p99/max 세트.
② Statistics 표 수치를 그대로 결과서에 — 램프업 포함 수치다. summarize-jtl.sh로 정상상태 재계산.
③ 발생기 에러를 서버 탓으로 — Can't assign requested address는 발생기 포트 고갈. 캘리브레이션 없이 낸 결론은 무효.
④ TPS 그래프만 보고 합격 선언 — TPS는 타이머가 지켜준 것일 수 있다. 응답시간 추이가 진짜 성적표.
⑤ 그래프 캡처 없이 숫자만 제출 — 증적 최소 세트는 TPS + Response Times Over Time 캡처 2장.
