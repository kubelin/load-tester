03 — 어디서 벌어졌나

지연은 서버가 아니라 발생기에서 벌어졌다

틱 간격이 요청값 대비 몇 배로 늘어났는지. 서버는 5,000 send/s까지 1.0–1.06배로 붙어 있다가, 연결 5,000개를 한 박스에서 감당하려는 순간 1.66배로 튄다 — 이건 서버 지연이 아니라 클라이언트 이벤트루프 포화다(틱은 다 도착, 읽기만 지연 = 누락 0).

04 — 죽이러 갔지만

두 번의 kill 시도, 둘 다 서버는 멀쩡

05 — 왜 안 죽었나

서버의 실제 한계는 아직 저 위에 있다

  • 4스레드 executor가 병목이 아니었다. 서버 자체검증에서 12,000 세션 × 1틱/s = 12,000 send/s를 누락 0으로 소화(72만 틱). hello 1000 기준 수만 세션까지 여유.
  • 느린 소비자는 send를 못 막았다. Tomcat blocking write는 소켓 send 버퍼가 찰 때까지 안 막힌다. 틱 250 B로는 세션당 1–2천 틱을 흡수 → 버퍼가 차기 전에 하트비트(무송신 세션)가 세션을 정리.
  • 병목은 발생기였다. 2코어·1.5 GB 단일 박스는 asyncio 이벤트루프·메모리(연결당 164 KB) 때문에 ~5,000 연결에서 포화. 서버 천장(90k)의 1/18.
  • 다음 병목 예상 순위 (대규모 분산 부하 시) ① 힙 (세션당 90 KB) → ② 커널 mbuf (nmbclusters 131,072) → ③ FD 90,000. executor는 그 뒤.
06 — 진짜로 죽이려면

다음 단계

한 대로는 못 죽인다는 게 결론. 서버의 실제 breakpoint를 보려면 부하를 물리적으로 키워야 한다.

발생기 분산

레포 agent(분산) 모드로 다수 IP·호스트에서 수만 연결 동시 투입. 단일 IP ephemeral 상한(~28k)과 2코어 한계를 넘어 힙·mbuf·FD를 실제로 압박.

대용량 payload 슬로우 킬

느린-소비자에게 100 MB–1 GB payload를 물려 send 버퍼를 빠르게 채움. 250 B 틱보다 훨씬 빨리 socket write 블록을 유발 → 단일 박스로도 (C) 재현 가능.

발생기 튜닝

포트 범위 1024–65000 확장(+예약 포트), 다중 프로세스 샤딩으로 코어당 이벤트루프 분리. 그래도 근본은 코어·메모리 증설.

부록 — 기록해 둘 것

테스트 중 건진 것들

macOS JVM FD 함정

HotSpot이 기동 시 soft FD를 OPEN_MAX 10,240으로 덮어써, cap을 아무리 올려도 ~1만 연결에서 Too many open files. -XX:-MaxFDLimit + MAVEN_OPTS에도 동일 옵션(mvn JVM이 자식에 물려줌)으로 90,000 확보.

클라이언트 auto-PONG

서버는 무송신 60s 후 PING, PONG 3회 무응답 시 close 1001. python websockets는 서버 PING에 자동 PONG → 200s 무송신에도 0 드롭. JMeter로 장시간 시엔 PONG 자동응답 여부를 별도 확인 필요.
