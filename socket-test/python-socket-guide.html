2. 소켓 몇 개까지 커버되나 — 발생기 용량

핵심: 한계는 CPU·메모리가 아니라 임시 포트(ephemeral port)다. 소켓 하나 = 출발 포트 하나. 단일 서버(IP:포트)로 연결할 때 동시 연결 최대 = 임시 포트 개수.

공식
한 발생기의 동시 소켓 최대 ≈ 임시 포트 개수  (단일 타겟 기준)
전체 = 발생기 대수 × 발생기당 포트 수  (스웜)

발생기 1대 상한 (단일 타겟)

환경 / 설정임시 포트 범위최대 동시 소켓
macOS 기본49152–65535~16,000
macOS (포트 확장)32768–65535~32,000
Linux 기본32768–60999~28,000
Linux (포트 확장)1024–65000~64,000

포트 외 자원은 대개 여유: 메모리 연결당 ~164KB(3만 연결 ≈ 5GB), FD는 ulimit -n을 연결 수 이상으로. 단, Python은 프로세스당 1코어라 수신율이 높으면 CPU가 먼저 찰 수 있다.

⚠️ 멀티 프로세스로도 포트 상한은 못 넘는다. run-ws-multi로 프로세스를 8개 띄워도 임시 포트는 머신(출발 IP) 단위로 공유. 8프로세스 × 4천 = 3.2만이 아니라, 합쳐서 ~포트수가 상한. 멀티프로세스는 CPU를 더 쓰려는 것이지 포트를 늘리는 게 아니다.

그 이상 — 스웜 (여러 발생기)

포트 풀을 늘리는 게 아니라 출발 IP를 늘려야 한다. 발생기 N대면 각자 포트 풀을 가지므로:

구성커버 가능 소켓
발생기 1대 (Linux, 포트 확장)~64,000
발생기 3대 (스웜)~19만
발생기 10대 (스웜)~64만

그래서 6만+ 연결은 반드시 run-ws-swarm(여러 호스트)으로. 이게 "서버가 여러 곳에서 연결받는 구조"가 필요한 실질적 이유다.

WebSocket은 HTTP보다 포트 압박이 크다. HTTP는 keep-alive로 커넥션을 재사용하지만, WebSocket/TCP 세션은 연결 하나가 포트 하나를 끝까지 점유한다. 그래서 "동시 유지 소켓 수"가 곧 포트 수에 직결된다.

3. 측정 모드 — ws_loadclient.py

pip install --user "websockets==8.1"
# <연결> <간격ms> <지속s> <호스트> <포트> <경로> <램프s>
python3 scripts/ws_loadclient.py 500 100 120 10.0.0.50 8080 /ws/test 8
WS_LOG=1 python3 scripts/ws_loadclient.py ...     # 결과 파일 저장
STALL_N=250 python3 scripts/ws_loadclient.py ...  # 느린소비자 250개 (executor 고갈 유도)

출력: 연결 성립/거절, seq 누락, hello→첫틱 p50/p99, 틱 간격 p50/p99, 세션별 p99 분포, 종료코드.

4. 수신 저장 모드

4-A. WebSocket (JSON 구독)

WS_SUB='{"header":{"tr_id":"H0STCNT0"},"body":{"input":{"tr_key":"{KEY}"}}}' \
WS_SUBKEYS='005930,000660' \
./scripts/run-ws-stream.sh 20 10.0.0.50 8080 /ws/quote 120

{KEY}=종목(라운드로빈), {IDX}=연결번호 치환. 구독 JSON은 시스템마다 자유.

4-B. 생 TCP (고정길이 전문)

TCP_MSGLEN=200 TCP_SUB='SUB|{KEY}' TCP_SUBKEYS='005930' \
TCP_DUMPFMT=text TCP_ENCODING=euc-kr \
./scripts/run-tcp-stream.sh 20 10.0.0.50 9000 120

저장 형식: hex(바이너리 안전) / text(디코드) / raw(.bin 원본). 국내 FEP 전문은 euc-kr 흔함.

저장 결과 (공통)

dumps/conn_<idx>.dat    # start .. ← 시작시각
                        <수신ms>  <원문 그대로>
                        # end .. records=.. ← 종료시각+집계
dumps/*_sessions_*.csv  연결별 시작/첫수신/마지막/종료 시각 + 수신 개수·바이트
대량 + 전체저장은 디스크 폭발. 5천연결 × 10msg/s × 180s = 900만 줄. 대량은 WS_DUMP=0 / TCP_DUMP=0, 데이터 확인은 소수 연결이나 DUMP_N=50(앞 50개만) 표본으로. 원문 저장은 연결당 FD를 1개 더 쓴다(소켓+파일).

5. 대량 부하 — 서버 실한계 찾기

# 한 박스 멀티프로세스
./scripts/run-ws-multi.sh 20000 10.0.0.50 8080 /ws/test 1000 180 8
# 여러 발생기 (서버가 여러 IP에서 연결받음)
./scripts/run-ws-swarm.sh "load@10.0.0.11,load@10.0.0.12" 40000 10.0.0.50 8080 /ws/test 1000 180
# 사다리로 한계 탐색
for N in 20000 40000 60000; do ./scripts/run-ws-multi.sh $N 10.0.0.50 8080 /ws/test 1000 120 8; done
합산 판정 신호의미
거절(close 1003) 증가서버 커넥션 상한 = 연결 한계
seq 누락 발생서버 데이터 유실 = 처리 한계
틱 간격 p99 ≫ 요청 간격스트리밍 지연 = cadence 한계
거절·누락 없이 오류만발생기 포화 → 스웜으로 호스트 더 늘려 재확인
